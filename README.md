# טפסי התחייבות לאקסל

מערכת שקולטת טפסי התחייבות (PDF סרוק, תמונה מהטלפון או טופס כתוב ביד), מחלצת מהם את השדות
בעזרת Gemini 3.8 Flash, מסמנת בכתום שדות לא בטוחים, מאפשרת בדיקה ותיקון, ומייצאת לאקסל.

## מבנה הפרויקט

```
lab-commitments/
├── backend/                 שרת API (FastAPI) - כל הלוגיקה
│   ├── app/
│   │   ├── main.py          הכתובות של ה-API
│   │   ├── auth.py          כניסה: סיסמה מוצפנת, ניתוק אחרי חוסר פעילות, חסימת ניחושים
│   │   ├── jobs.py          עיבוד ברקע + דיווח התקדמות
│   │   ├── records.py       מה קורה כשמתקנים תא / מאשרים שורה
│   │   ├── repository.py    כל הגישה למסד (SQL רק כאן)
│   │   └── core/            מנוע הפענוח (מהפרויקט הקודם)
│   │       ├── prompts.py         ההנחיות ל-Gemini
│   │       ├── extractor.py       הקריאה ל-Gemini
│   │       ├── pipeline.py        קובץ -> עמודים -> פענוח -> נרמול -> מיזוג עמודי המשך
│   │       ├── validation.py      ת.ז., תאריכים, מספרים, גורם שולח
│   │       ├── image_utils.py     PDF לתמונה, יישור, חידוד
│   │       ├── exporter.py        אקסל
│   │       └── sending_entities.txt   הרשימה הסגורה של גורמים שולחים (עריכה בלי קוד)
│   ├── tests/
│   └── requirements.txt
├── frontend/                הממשק (Streamlit) - מציג בלבד, פונה לבקאנד
│   ├── app.py
│   ├── api_client.py        כל הפניות לבקאנד
│   ├── styles/style.css     העיצוב
│   ├── .streamlit/config.toml
│   └── requirements.txt
├── db/
│   └── schema.sql           מבנה הטבלאות (רץ אוטומטית בהפעלת הבקאנד)
├── render.yaml              הגדרת הפריסה ל-Render
└── .env.example             תבנית להגדרות
```

**איך החלקים מדברים:** הממשק ← (HTTP + אסימון התחברות) ← הבקאנד ← Supabase (PostgreSQL) ו-Gemini.
הממשק לא ניגש למסד ולא ל-Gemini, ומפתח ה-Gemini נמצא רק בבקאנד.

## שלב 1: מסד נתונים ב-Supabase (פעם אחת)

1. ב-[supabase.com](https://supabase.com): New project. שומרות את סיסמת המסד.
2. בפרויקט: **Connect**. בוחרות **Session pooler**, לא Direct connection, ומעתיקות את הכתובת.
   כתובת ה-Direct עלולה לא לעבוד מ-Render.
3. מחליפות בכתובת את `[YOUR-PASSWORD]` בסיסמת המסד. זה הערך של `DATABASE_URL`.

אין צורך ליצור טבלאות: הבקאנד יוצר אותן בהפעלה הראשונה מתוך `db/schema.sql`.

> המסד משותף לפיתוח ולאתר. לפני ההגשה כדאי לנקות נתוני ניסוי ("ניהול נתונים" ← "מחק את כל הרשומות").

## שלב 2: הרצה מקומית (בלי Docker)

צריך Python 3.11 ומעלה.

```bash
# בתיקייה הראשית של הפרויקט
cp .env.example .env          # ממלאות: GEMINI_API_KEY, DATABASE_URL, APP_PASSWORD

python -m venv .venv
# Windows:  .venv\Scripts\activate      Mac/Linux:  source .venv/bin/activate
pip install -r backend/requirements.txt -r frontend/requirements.txt
```

מפעילות בשני חלונות טרמינל:

```bash
# חלון 1 - בקאנד
cd backend
uvicorn app.main:app --reload --port 8000
```

```bash
# חלון 2 - ממשק
cd frontend
streamlit run app.py
```

נכנסות ל-http://localhost:8501 עם `APP_USERNAME` ו-`APP_PASSWORD` שהגדרתן.

## שלב 3: העלאה ל-Render

1. מעלות את הפרויקט ל-GitHub. הקובץ `.env` לא עולה, הוא ב-`.gitignore`.
2. ב-Render: **New ← Blueprint**, ובוחרות את ה-repo. Render קורא את `render.yaml` ויוצר שני שירותים.
3. Render יבקש את הערכים הסודיים:
   - **lab-backend:** `GEMINI_API_KEY`, `DATABASE_URL` (מ-Supabase), `APP_PASSWORD`.
   - **lab-frontend:** `BACKEND_URL`. בפעם הראשונה אפשר להשאיר ריק.
4. כשהבקאנד עולה, מעתיקות את הכתובת שלו (למשל `https://lab-backend-xxxx.onrender.com`).
   ב-lab-frontend: **Environment ← BACKEND_URL** ← מדביקות ← Save. השירות יופעל מחדש.
5. נכנסות לכתובת של **lab-frontend**. זה האתר.

**לשים לב:**
- בתוכנית החינמית של Render שירות נכנס למצב שינה אחרי זמן בלי שימוש, והכניסה הראשונה אחריו איטית (עד דקה). לפני הדגמה כדאי להיכנס לאתר כמה דקות קודם.
- בדקו בתוכנית החינמית של Supabase אם פרויקט ללא פעילות נכנס להשהיה. אם כן, היכנסו אליו לפני ערב הגמר.
- הבקאנד רץ עם worker אחד, כי משימות העיבוד נשמרות בזיכרון שלו. לא לשנות ל-`--workers 2`.

**החלפת סיסמה:** משנות את `APP_PASSWORD` ב-Render ← Save. בהפעלה מחדש הסיסמה מתעדכנת וכל המחוברות מנותקות.

## כללים שמומשו

- **לא מנחשים:** שדה שלא נמצא נשאר ריק ומסומן. שדה שהמודל לא בטוח בו, או שנכשל בבדיקה בקוד, מודגש בכתום.
- **כמה מספרי התחייבות בטופס אחד:** כל מספר הוא התחייבות נפרדת, ולכן נוצרת רשומה נפרדת לכל מספר.
  כל שאר הפרטים (שם, ת.ז., מספר מרכזי, תאריך, גורם שולח) זהים בכל הרשומות.
- **כמה מספרים מרכזיים:** נשמרים במסד כרשימה (`TEXT[]`), כל מספר בנפרד. בטבלה ובאקסל הם מופיעים
  באותו תא, מופרדים בפסיק: `947768, 947769`. בעריכה מקלידים עם פסיק.
- **שדה לא ודאי:** בטבלה מופיע בתא סימן ⚠️, והשורה מסומנת בצהוב עם ״יש לבדוק ולוודא את תקינות: ...״.
- **ת.ז.:** מושלמת ל-9 ספרות עם אפסים מובילים, ונשמרת באקסל כטקסט.
- **גורם שולח:** נבחר רק מתוך `sending_entities.txt`. "נותן השירות: שיבא" בטופס של קופה אינו הגורם השולח.
- **תיקון תא:** הכתום יורד רק מהתא שתוקן. השורה מאושרת כשמסמנים "אושר", או אוטומטית כשאין בה יותר תאים כתומים.
- **עמוד המשך** מזוהה וממוזג לטופס הקודם באותו PDF.
- **פרטיות:** תמונות הטפסים לא נשמרות כלל. הן נשלחות ל-Gemini לפענוח ונמחקות מהזיכרון. ביומן השרת לא נרשמים פרטים אישיים.

## אבטחה

- כל כתובות ה-API דורשות התחברות, חוץ מ-`/api/health`.
- הסיסמה נשמרת במסד מוצפנת (scrypt). האסימון נשמר כ-hash בלבד.
- ניתוק אוטומטי אחרי 60 דקות ללא פעילות (`SESSION_MINUTES`).
- חסימה ל-5 דקות אחרי 5 ניסיונות כניסה שגויים.
- ב-Supabase מופעל RLS על כל הטבלאות, כך שאי אפשר לקרוא אותן דרך ה-API הציבורי של Supabase.

## בדיקות

```bash
cd backend
pip install -r requirements-dev.txt
pytest -q
```

בדיקות המסד והשרת רצות רק כשמוגדר `TEST_DATABASE_URL`. **הן מוחקות את כל הנתונים במסד שהן רצות עליו**,
ולכן לא להריץ אותן על המסד של האתר, אלא רק על מסד בדיקות ריק.
